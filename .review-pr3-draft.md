## Blocking (1)

### 1. `@icp-sdk/auth` default idle handler logs users out + reloads page after 10 min of inactivity — `src/contexts/AuthContext.tsx:61, 88, 108`

Every `new AuthClient(...)` call site omits `idleOptions`, so the SDK installs its default idle callback at `node_modules/@icp-sdk/auth/dist/esm/client/auth-client.js:209-212`:

```js
this.idleManager?.registerCallback(() => {
  this.signOut();
  location.reload();
});
```

`IdleManager` default timeout is **10 minutes** (`@icp-sdk/auth/dist/esm/client/idle-manager.d.ts:25` — "By default, the IdleManager will log a user out after 10 minutes of inactivity"). For Nuance — a content reading platform — a user reading any article > 10 min gets silently signed out *and* has their page reloaded mid-read, losing scroll position and any in-progress UI state.

Old `@dfinity/auth-client` ships with the same default; old nuance.xyz inherits the bug. The rebuild is a chance to fix it.

**Suggested fix** in `AuthContext.tsx` — pass `idleOptions` to every `new AuthClient(...)`. Three reasonable shapes:

1. **Disable idle entirely (simplest):**
   ```ts
   new AuthClient({ idleOptions: { disableIdle: true } })
   ```
   Session lives until the 8-hour delegation expires.

2. **Disable default callback, soft-prompt at idle:**
   ```ts
   new AuthClient({
     idleOptions: {
       disableDefaultIdleCallback: true,
       onIdle: () => { /* surface a "stay signed in?" prompt */ },
     },
   })
   ```
   Requires the toast service from decision #22 — defer to that consumer.

3. **Lengthen the idle timeout for a reading platform:**
   ```ts
   new AuthClient({ idleOptions: { idleTimeout: 60 * 60 * 1000 } })  // 60 min
   ```
   Keeps the security posture; survives most read sessions.

Recommend **#1 for PR #3** (cheapest, fully fixes the bug; 8-hour delegation gives a natural ceiling). Revisit idle-driven security in a later PR with a real consumer.

## Major (3)

### 1. Figma `1:50034` and decision #24 are out of sync — `src/components/LoginModal/LoginModal.tsx:88-114` vs Figma

Figma node `1:50034` shows four buttons: **internet identity, NFID, Stoic, Bitfinity**. Implementation correctly ships **internet identity, Google, Apple, Microsoft** per decision #24 (which postdates the Figma file and supersedes it). But:

- Future `get_design_context` reads on Page 8 keep generating code that contradicts decision #24.
- "Pixel-perfect Figma fidelity is the project standard" (memory.md, lessons.md) is silently broken on Page 8.
- Anyone reviewing Page 8 work against Figma will be misled.

**Fix:** Update Figma `1:50034` to show the four decision-#24 providers. Until that happens, every PR touching Page 8 inherits this drift. If updating the Figma is non-trivial, at minimum add a note layer in the Figma frame pointing to decision #24, or a `docs/page-8-audit.md` stub flagging the divergence.

### 2. Stale `identity` / `principal` after failed logout — `src/contexts/AuthContext.tsx:114-119`

The catch block sets `status="error"` but does not clear `identity` / `principal`. `isAuthenticated` correctly resolves to `false` (it's derived from `status`), but `identity` and `principal` remain populated from the previously-authed state. PR #4's authed `ActorsContext` refactor will be the first consumer that reads `identity` directly and may see a non-null identity for an "unauthenticated" user.

**Fix:**
```ts
} catch (err) {
  if (!mountedRef.current) return;
  setIdentity(null);          // ← add
  setPrincipal(null);         // ← add
  setError(err instanceof Error ? err.message : "Sign-out failed");
  setStatus("error");
  throw err;
}
```

The symmetric concern in `login()`'s error path (`:97-101`) is more defensible — if a user is already authed and clicks login, preserving their prior identity on failure is arguably correct. Leave that one.

### 3. `aria-labelledby` missing on the modal Dialog — `src/services/modal/ModalProvider.tsx:47-63`

MUI Dialog is mounted without `aria-labelledby`. Screen readers announce the modal opens but not its title. The Modal service is intentionally unopinionated about appearance, but it should still ensure each modal has an accessible name.

**Fix:** Thread an optional `ariaLabelledBy` parameter through `open()`:

```ts
type ModalContextValue = {
  open: (content: ReactNode, opts?: { ariaLabelledBy?: string }) => void;
  ...
};
```

Then in `LoginModal.tsx:62`, add `id="login-modal-title"` to the h2; in Header/CtaBanner, call `modal.open(<LoginModal />, { ariaLabelledBy: "login-modal-title" })`.

## Minor

### Dead code in `loginModalCopy` — `src/constants/copy.ts:92-93`, `src/components/LoginModal/LoginModal.tsx:131`

- `loadingLabel: "Signing in…"` exported, never read.
- `errorFallback: "Sign-in failed. Please try again."` is unreachable — the `||` fallback at `LoginModal.tsx:131` sits inside `{error && (...)}` so `error` is always truthy when the JSX renders.

Either delete both, or wire `loadingLabel` into the disabled-button state (replace label while `isLoading`) and pick a real use for `errorFallback`.

### Hardcoded error color `#c62828` — `src/components/LoginModal/LoginModal.tsx:129`

Violates decision #21 ("colors centralized"). Either add `--color-error` to `@theme` and reference via `var(--color-error)`, or use MUI's `palette.error.main` through the `sx` prop.

### Microsoft `{tid}` placeholder — decision #24 "How to apply" is misleading

Decision #24's "How to apply" reads:

> Microsoft tenant ID: `'common'` (substituted into the URL `{tid}` placeholder).

But `@icp-sdk/auth@7.0.0` passes the `{tid}` placeholder verbatim to id.ai as the `openid` search param (`auth-client.js:46`). id.ai handles tenant resolution server-side (per `tasks/todo.md:306`). The implementation correctly does nothing — but the decision text implies our code does the substitution.

**Fix:** Update decision #24's "How to apply" to clarify: "Microsoft tenant resolution happens server-side at id.ai. No client-side substitution required. `AuthContext` stays config-free for this."

### `AuthClient` instantiated multiple times per session — `src/contexts/AuthContext.tsx:61, 88, 108`

Mount restoration creates one, each `login()` click creates one, `logout()` creates one. Each construction does two IndexedDB reads (`#hydrate()` → `restoreKey` + `restoreChain`) plus an ECDSA key generation. Wasteful but not broken.

A singleton `AuthClient` (created lazily in AuthContext via `useRef`) would be cleaner and would also simplify Blocking #1 (configure `idleOptions` once instead of N call sites). Not required for PR #3 — flag for the next auth-touching PR.

### `react-refresh/only-export-components` lint errors — `AuthContext.tsx:139`, `ModalProvider.tsx:68`

Same pattern as the pre-existing violation in `ActorsContext.tsx:54`. Affects Vite Fast Refresh only — no runtime impact. Splitting each hook into a sibling file (`useAuth.ts`, `useModal.ts`) clears all three at once. Defer or fix in a one-shot follow-up.

### `status: "loading"` covers both restore and active sign-in — `src/contexts/AuthContext.tsx:42`

A consumer that wants to render a spinner only during active sign-in can't distinguish from initial mount-time restoration. Not a problem today; flag if PR #4 needs the distinction (e.g., the welcome-banner skeleton state).

### `Link to="/about"` in Header is a broken route — `src/components/ui/Header.tsx:26`

Pre-existing from PR #2, not PR #3 scope, but visible in the diff context. Either remove the link or stub the route.
